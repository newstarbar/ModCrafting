# ModCrafting 创作工作台需求

日期：2026-10-16。状态：首轮 R1/R2 五种基础配方及 R3 六类声明式内容参数闭环已实施并实机验证；R4 基础 Screen/配置页面/HUD 也已完成首轮闭环；R5 的方块/物品体素模型首轮（AI DSL + Three.js 编辑器）已实施，实体动画与外部格式导入仍开放；R6/R7 及复杂容器尚未实现。R5 首轮证据见[体素模型归档](../../docs/archive/2026-10-26-ai-voxel-model.md)。R4 证据与限制见[界面归档](../../docs/archive/2026-10-16-mc-gui-workbench.md)。R3 证据见[内容参数归档](../../docs/archive/2026-10-16-content-parameter-workbench.md)。交付证据见[配方归档](../../docs/archive/2026-10-15-recipe-creator-workbench.md)，不将本需求文档视为全部已交付。

## 目标与当前缺口

工作台承接旧 Desktop 的 Minecraft 专属创作体验，让用户与外部 Agent 一起设计、调整并验证内容。环境、构建、日志和验收是辅助能力。目标闭环为：想法 → Agent 方案/工程草稿 → 用户可视化编辑 → 确认变更 → 工程产物 → 游戏内验证 → 继续修改。

当前 Web 已有工程环境、构建、游戏启停、观察测试、任务报告和首轮配方工坊；不能视为 Desktop 创作能力全部替代。旧配方纯逻辑已共享，六类参数表单与资源纹理预览已迁入新 Web，R4 基础 GUI 画布/安全写回与实机交互已补齐，复杂容器同步另验。3D 完整编辑、建筑生成和 AI 整合包流程是新增/未来能力，不能列为旧代码已实现。

“MC UI”指模组内的 Screen、配置页面、容器界面和 HUD 的创作，不只是给工作台换 Minecraft 风格皮肤。物品、方块、实体/生物均纳入参数创作范围。

## 用户故事与验收要求

### R1 共同创作与工程一致性

- 当用户打开工程时，工作台应提供内容对象导航和对应专用编辑区，优先显示创作入口，并能进入构建/游戏/验收辅助区。
- 当 Agent 生成方案或用户在 Web 修改时，两者应指向同一个工程内容与草稿版本；Agent 能读取用户确认后的结构化修改，而不是依赖截图猜测或要求用户手抄 JSON。
- 当用户确认应用时，系统应展示目标文件及变更摘要，保存后重新读取并验证；当文件已被外部 Agent 修改时，应提示冲突并重新加载/合并，不能静默覆盖。
- 当用户取消、刷新或重开会话时，已保存工程内容应保持一致；未应用草稿与已写入工程应有明确区分。
- 对产品生成或支持的声明式内容应提供可编辑参数；当第三方/手写源码无法可靠解析时，应保留代码并说明可编辑范围，交由宿主 Agent 处理，不以默认值覆写未知逻辑。
- Web 和 MCP 通过同一 Core 业务操作处理创作数据；仅按实际模块增加必要契约，不为未来一次性建设通用编辑器框架。UI 关闭不影响已提交的构建/测试任务。

### R2 配方工作区

- 当编辑有序合成时，应提供 3×3 网格、可搜索的原版/工程物品、拖放/替换/清空、结果物品和结果数量，并预览实际配方。
- 当切换无序合成或熔炼等类型时，应使用对应材料列表、经验/时间等适用字段，不能把所有配方硬塞入同一个九宫格。
- 当指定 tag/替代材料或错误 ID 时，应分别正确呈现或报错；同一个材料在不同槽位的重复与单个材料栈数量不得混淆。
- 当用户应用配方时，应生成/修改 Fabric 1.21.4 正确目录与格式的资源，读回后保持语义等价；原版 ID 与属性来自 knowledge lookup，工程自定义 ID 来自工程。
- 首个闭环验收：打开真实配方 → 拖放替换一个材料、修改产物数量 → 预览变更 → 写入 → 刷新读回 → Agent 读取相同内容 → 构建 → 专用游戏世界确认产物。不以静态网格演示代替这一闭环。

### R3 物品、方块与实体/生物参数

- 当用户选择内容对象时，应显示适用参数、单位/范围、图标/外观和资源关联；不适用字段应隐藏或解释。
- 范围包含：物品堆叠与耐久、食物属性；方块硬度、抗性等；生物生命值、速度、攻击等；工具/护甲的对应属性。具体字段先核对旧 schema 和目标版本，不把自由文本“特殊效果”当作已实现的任意行为编辑器。
- 当参数超出版本或类型限制时，应在提交前指出；参数修改应能写回受支持的工程内容、重新加载并在实际游戏中验证相应变化。
- 原版基准从知识工具查询；生物复杂 AI、事件逻辑与原有手写源码通过 Agent 协作，不承诺用若干滑块表达全部逻辑。

### R4 MC 界面创作

- 当用户编辑受支持的 Screen/HUD 布局时，应有画布、组件选择、属性检查、拖拽/尺寸调整、网格吸附、对齐和不同 GUI 缩放/窗口比例预览。
- 布局应包含稳定元素 ID、类型、位置、尺寸、样式及受支持的事件/数据绑定；按钮点击、开关、滑块和容器槽位须区分预览行为与游戏真实行为。
- 当用户确认布局时，应将结构化结果交回工程/Agent，生成或更新对应代码，并在游戏实际 Screen/HUD 中核对；不只保存一张 HTML 预览图。
- 初期优先旧组件已支持的配置页面与基础 Screen/HUD；复杂容器/服务端同步能力单独验收，不把拖放 HTML 成功等同 MC 容器可交互。
- 复用旧 iframe 逻辑前，应核对消息来源和结构化数据、脚本/事件处理边界，不能直接把原始 AI HTML 当作可信执行代码。

### R5 3D 模型可视化与编辑（方块/物品首轮已交付）

- 首轮（2026-10-26）：方块/物品走自研体素 DSL（`fabric_voxel_workspace`）+ Three.js 体素画布，旋转/增设/涂色/擦除/镜像/撤销，保存导回工程并生成确定性图集与模型 JSON；证据与限制见[体素模型归档](../../docs/archive/2026-10-26-ai-voxel-model.md)。原"优先评估 Blockbench"路线改为自研轻量编辑器：Blockbench 双向保存/嵌入未验证，体素范围先自研，复杂网格格式后续仍可评估。
- 仍开放：实体模型与动画、外部网格格式（OBJ/GLB/Blockbench 文件）导入、参考图转体素；接入前需小样验证格式兼容，不能将格式转换成功当作游戏显示正确。
- 模型源格式、Minecraft 运行时格式、纹理和实体动画分别声明支持范围；导入/导出须保留可编辑源文件（当前可编辑源即 content 对象中的 DSL）。

### R6 建筑生成（游戏内展示）

- Web 应提供建筑需求/规格摘要、目标实例/专用世界、区域/规模提示、执行确认、进度与结果入口；空间预览与摆放效果在 Minecraft 中展示，不在 Web 重做世界编辑器。
- 当执行摆放时，应核对世界、区域、规模和对应恢复策略；与现有小范围测试区不兼容时需单独设计，不能放宽现有验收护栏后声称支持任意建筑。
- 当用户取消或生成失败时，应停止后续操作并报告已经修改的范围；恢复能力必须经过验证，不能承诺未实现的整世界撤销。

### R7 AI 模组整合包创作（独立后续主线）

目标流程：用户想法 → 玩法与版本约束 → 跨平台检索候选 → 解释匹配与缺口 → 用户调整组合 → 锁定依赖/版本/客户端服务端范围 → 隔离安装 → 冲突复现与定位 → 最小调整/改造/兼容模组 → 回归 → 导出可复现整合包。

- 当用户描述玩法时，外部 Agent 应规划与选择；Web 展示“需求—候选模组—已覆盖/缺失功能”、来源/作者/版本/依赖、替换比较与选择操作。Core 提供确定性的检索适配、清单、下载校验、实例与验收，不内建新模型循环。
- 当搜索 Modrinth、CurseForge 等平台时，应使用官方 API/平台允许的访问方式，保留项目/文件 ID 与来源；平台不可用、缺 API 权限或无合适版本时应如实显示，不伪造匹配或绕过分发限制。
- 当确定组合时，应记录 MC/Loader/Java 版本、文件版本/哈希、依赖、客户端/服务端范围和配置覆盖，校验可复现安装与导出；优先评估 packwiz，避免先写通用包管理器。
- 首个可运行版本沿用现有 Fabric 1.21.4 验收能力；其他 MC 版本/Forge/NeoForge 等作为明确扩展矩阵，不能将平台搜索覆盖等同运行兼容。
- 当无精确匹配时，应展示“采用相近模组并配置/资源或数据包调整、合法源码改造、编写独立补充/兼容模组、重新实现缺失功能”的候选与成本，再执行选定方案。
- 当出现冲突时，应先保留可复现组合与日志，区分依赖/版本、配置、资源/数据覆盖、代码/Mixin 和运行时玩法冲突；优先已有版本/配置/既有兼容方案，再处理源码或兼容模组，不默认修改第三方 JAR。
- 当声明“修复成功”时，应在隔离实例复验原失败条件和关键玩法，并记录改动来源、范围与仍未覆盖的组合；不能只以启动成功替代功能兼容，不能承诺任意冲突均可自动修复。
- 对第三方源码修改和产物分发需核对其许可证与平台条件，保存作者/许可证信息。没有改造/分发依据时应提供替代模组或独立补充方案；不把“可下载”解释为“可任意修改再发布”。

## 建议实施顺序与退出门槛

不新增 P6/P7 等阶段编号；沿原路线补齐 P3 创作迁移，P5 的完整功能替代保持未完成。

1. **先交付一条真实配方编辑闭环（R1/R2）**：复用网格/物品组件，贯通 Agent ↔ Web ↔ 工程 ↔ 游戏；这会验证创作状态、保存、冲突处理和读回，而不是继续加监控卡片。
2. **内容参数与 MC UI（R3/R4）**：逐项迁移现有表单与画布，补齐各自落盘/游戏验收；不要求等所有对象完成才展示首个可用编辑器。
3. **3D 与建筑入口（R5/R6）**：先完成成熟工具接入评估与支持格式/世界边界，再交付实际导回/游戏展示。
4. **整合包流程（R7）**：先完成需求匹配、组合与可复现安装，再逐类实现冲突诊断/调整/兼容模组闭环；与单模组创作共用资产和验收能力。

创作能力完成标准是“用户能看见、能调整、能写回、Agent 能接续、游戏能验证”。旧 P3 执行流程的既有通过结果保留；新的创作验收逐项记录，不能由旧 19 工具连接或接口状态检查代替。

## 成熟方案调查（2026-10-15）

- [Blockbench 官方仓库](https://github.com/JannisX11/blockbench)及 [Web URL 参数](https://blockbench.net/wiki/docs/url-parameters/)：已有 Minecraft 模型编辑与通过链接载入模型的机制；GPL-3.0。作为模型编辑候选，不等于已经解决双向保存/嵌入或本项目格式兼容，接入前需小型样例验证。
- [packwiz 官方文档](https://packwiz.infra.link/)及[源码](https://github.com/packwiz/packwiz)：MIT，TOML 清单、Modrinth/CurseForge 支持与导出是可复用候选；属于外部 CLI，需评估 Windows 分发、固定版本/哈希、维护与安装成本，不是当前已安装依赖，也不提供任意冲突修复。
- [Modrinth 官方 API](https://docs.modrinth.com/api/)和 [CurseForge 官方 API](https://docs.curseforge.com/rest-api/)：检索与文件元数据的依据；CurseForge 的 API 访问和分发标记等条件需在接入时核对。当前只读研究，不请求密钥、不安装/下载模组、不改真实宿主配置。

本草案之外：不恢复 Electron 主入口，不重建聊天/模型系统，不先扩展 Loader/OS/MC 版本矩阵，不推送/发布，不删除任何用户文件。所有后续实现继续在隔离 Worktree，pnpm 共享 Store、各自 node_modules。
